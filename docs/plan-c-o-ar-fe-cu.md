# План: базы Fisher для C, O, Ar, Fe, Cu

Задание: сделать базы в формате Фишера для углерода, кислорода, аргона,
железа и меди. Для Ar, Fe, Cu максимальное спектроскопическое число — 6.
Данные из Питера. Если есть сечения ионизации электронным ударом — брать
их. Недостающие добить табуляцией Бернштама и Лотца.

Файлы Fisher создаются параллельно NOMAD через
`create_all_from_databases.py`.

## Вопросы и ответы

1. До какого sp-числа делать C и O?
   C — до ядра: sp 1–6 + nucleus 7 (в `db/C/levels` уже 1–6).
   O — до 6–7. Существующий NOMAD `db/O/IN1.INP` — это 1–8 + nucleus 9,
   energy-limits = IP:
   `1:13.62,2:35.12,3:54.94,4:77.41,5:113.90,6:138.12,7:739.33,8:871.41`.
   Для нового прогона брать эти IP как основу; max-sp 6 или 7
   (не 8). Пока в плане: O max-sp = 7, без O VIII.

2. Какие `energy-limits`?
   Как у NOMAD-кислорода: отсечка = ionization potential вида
   (первая строка `Limit` в Piter levels). Для C из `db/C/levels`:
   `1:11.26,2:24.38,3:47.89,4:64.49,5:392.09,6:489.99`.

3. Какой `nmax` / какие уровни?
   До sp 6 — только одиножды возбуждённые. В коде сейчас нет такого
   фильтра: `should_include_level()` режет лишь `n > 6` у последнего
   орбитала и `?1`. Существующий `db/O/IN1.INP` шире (есть и 2s-дыры,
   и высокие конфигурации с n≤6). Фильтр «только singly excited»
   ещё предстоит сделать или уточнить правило.

4. Есть ли у Питера сечения ионизации электронным ударом?
   Нет. Atomic Line List даёт только уровни, радиационные линии и
   ionization limits. Нет EII/EIE сечений, автоионизации и фотоионизации.
   Подробнее: `docs/scripts.md`, раздел «Что есть у Питера и чего нет».

5. Нужен ли полный Fisher-комплект?
   Нужны `QSs`, `Exc`, `Inz`, `AIw`. `Params` не нужен.
   Из этой ветки всегда писали только `QSs` и `Inz`.
   `Exc` = тот же формат, что NOMAD `EXCIT.INP` (отдельного конвертера нет
   и не нужно: копировать/переименовать).
   `AIw` = тот же заголовок, что NOMAD `AIW.INP`. Сборщик `create_aiw()`
   есть только для FAC (`fac.ai`). У Питера AI-уровней нет, файл будет
   пустым (один заголовок).

6. Сломан ли дамп `BCFP.INP.fisher`?
   Был сломан на чистом Питере: фиты считались в памяти, файл писался
   только при `--replace-starting-from`. Починен: дамп
   `BCFP.INP.fisher` и обновлённого `EXCIT.INP` всегда.

7. Откуда ионизация / Strasbourg / формула?
   Фотоионизация/RREC: Strasbourg где есть, формула только в дырах.
   EII у Strasbourg не используется.
   EII для отправки Фишеру — цепочка Бернштам→таблица→Лотц (см. ниже).

8. Докачивать недостающие `lines`?
   Да. Скачаны заново:
   - `db/Fe/lines/1.txt`, `3.txt` — нормальные объёмы;
   - `db/Cu/lines/3.txt` — нормальный;
   - `db/Cu/lines/4.txt`–`6.txt` — у Питера почти пустые
     (единицы–десятки M1-линий, файлы 1–2 КБ).
     Для Cu IV–VI радиационный `SPECTR`/`EXCIT` будет очень бедный.

9. Неудачные фиты ионизации удалять или оставлять нули?
   Отмечать, не удалять. Потом решим, что с ними делать.
   В коде сейчас `remove_bad_fits=True` — перед прогоном нужно
   `False`: нули и комментарий `# Can't create fitting params`.

10. Сетка табуляции `1..100 eV`, шаг `1` — это то, что нужно?
    Да, 1–100. Так уже задано в `lib/bcfp.py` (`START_E`/`END_E`).

11. Какой runtime: Code1 или Code2?
    Code 2: `QSs` с полем `a24`, AI отрицательные (у Питера AI нет),
    счётчики `StrExc`/`StrInz`/`StrAIw` если понадобятся. `Params`
    не делаем.

## Как устроено в коде сейчас

**RREC (фотоионизация, Strasbourg TOPBASE)**

- `create_rrec_from_in1(..., use_formula)` — переключатель **весь элемент**, не переход.
- `use_formula=True` → все переходы формулой (`write_rrec_from_formula`).
- `use_formula=False` → все переходы Strasbourg (`write_rrec_from_strasburg`).
- Если Strasbourg не нашёл уровень/сечение — печать `NO LEVELS FOUND` и
  **пропуск**. Fallback на формулу **нет**.
- CLI `create_all_from_databases.py`: после разбора
  `use_formula = (use_formula == 'formula')` при уже-bool → всегда
  `False`, то есть всегда ветка Strasbourg (и падение, если файла cuts нет).

**EII (электронный удар, Inz / BCFP)**

- Strasbourg **не участвует**.
- `create_bcfp_from_in1` строит branching ratio по конфигурациям.
- `create_fac_fitting_params`: dat из `ionization-crosssection/`, иначе
  табуляция Бернштама (`s/p/d`) или Лотца. Это уже «база, иначе формула».
- `remove_bad_fits=True` — плохие фиты **удаляет**, а не помечает.

**Страсбург на диске** (`db/<elem>/strasbg-cuts`) — перекачано / проверено 2026-09-02

| Элемент | Cuts с данными | В TOPBASE нет |
|---|---|---|
| C | 1–7 | — |
| O | 1–9 | — |
| Ar | 1–8 | — |
| Fe | 3–8 | I, II (`VIEW-BUFFER EMPTY`) |
| Cu | — | все I–VIII: `INVALID NZ RANGE` (Z=29 вне TOPBASE, база до Fe) |

Дыры Fe I–II и всей Cu **не страшны по заданию**: RREC там формулой.
Код этого fallback **пока не чиним**: Strasbourg-промах сейчас = пропуск
перехода, не формула. Для C и O дыр нет, fallback не нужен.

`read_strsbrg_db` открывает файл на каждый sp; пустой cuts не даёт
формулы, а отсутствующий файл уронит прогон.

## Первый элемент: углерод (не кислород)

Углерод проще:

- 6 ионов + ядро vs у O семь (max=7) и путаница с уже лежащим
  `db/O/IN1.INP` (там 1–8 + nucleus 9, без singly-excited).
- Strasbourg levels/cuts 1–6 полные — RREC без fallback и без `--formula`.
- Граница «до ядра» однозначная. У O ещё решать 6 vs 7 vs старый 8.
- Piter levels/lines 1–6 на месте.

Кислород оставляем вторым: готовый NOMAD O — референс для сравнения,
не первый прогон.

**Что для C менять в коде**

Не нужно для самого прогона C (данные есть, CLI и так идёт в Strasbourg):

- fallback RREC Strasbourg→формула;
- починка флага `--formula`.

Нужно, иначе C не совпадёт с заданием / с двумя этапами EII:

1. Переключатель Бернштам vs Лотц. Сейчас в одном прогоне
   `create_cross_section_function()` сам выбирает: потерянный электрон
   в `s`/`p`/`d` → Бернштам–Радченко, иначе Лотц. Двух запусков
   «сначала всё Бернштамом, потом всё Лотцем» **нет**.
2. Табуляция 1–100 и запись таблиц. `create_tabulation_files=False`;
   если включить — упадёт (`in1_path` в методе не определён).
3. `remove_bad_fits=False` (отмечать, не удалять).
4. Фильтр «до sp 6 только одиножды возбуждённые».

## EII: зачем Бернштам, а Фишеру — Лотц

Старый код Фишера (его собственный, не наш Code 2) **не умеет** считать
сечение по формуле Бернштама. Он принимает только формулу **#4**
(4 коэффициента EII в `Inz`; иначе `STOP ... formula# ne 4`).
Бернштам при этом точнее.

Поэтому цепочка такая, не два независимых прогона:

1. Посчитать σ(E) по Бернштаму.
2. Протабулировать (сетка 1–100, шаг 1).
3. Эту таблицу отфитировать формулой Лотца (#4).
4. Послать ему **весь набор файлов уже с фитами Лотца** и номером
   формулы Лотца (#4). Бернштамовские коэффициенты ему не нужны.

Это не «два комплекта Inz на выбор». Промежуточный Бернштам — только
чтобы получить точную таблицу. В поставке — Лотц.

**Что сделали на C и почему это не то**

Сделали два полных независимых прогона:

- `out/bernstam/C` — σ Бернштама, таблица, фит тем же 4-параметрическим
  `approximation_fun` (это как раз форма #4). По смыслу ближе к цели:
  Бернштам → таблица → коэф. #4.
- `out/lotz/C` — σ сразу по аналитическому Лотцу, фит #4 уже по лотцевой
  кривой. Это **не** «таблица Бернштама, отфитированная Лотцем».
  Для посылки Фишеру не использовать.

Следующий правильный шаг: явно фитить таблицы из
`out/bernstam/C/tabulation/` формулой #4 и писать Fisher `Inz` с Mthd 4.
Не пересчитывать σ по Лотцу с нуля.
